# Versioning and releases

Use MAJOR.MINOR.PATCH: breaking changes, compatible functionality, compatible fixes
respectively. Documentation corrections tied to a release may increment PATCH.
The manifest currently declares 0.1.0; no published product history was found in
the initial inspection. Constitution 1.0.0 is governance metadata.

Only after the user confirms completion, inspect manifests, CHANGELOG.md and tags;
choose the next version from actual history and change impact. Use dated, newest
first entries with Added/Changed/Deprecated/Removed/Fixed/Security as appropriate.
Describe user-visible outcomes and link tickets or docs per branching.md.

Release tags are annotated `vMAJOR.MINOR.PATCH`. An alpha may use, for example,
`v0.1.0-alpha.1`, then alpha.2; prereleases precede the corresponding stable release.
Examples below are reference syntax, not a recommendation to release now:

```sh
git tag -a v<version> <commit-sha> -m "v<version>"
git push origin v<version>
```

Validate the intended commit before tagging. Agents may recommend concrete
commands after completion confirmation, but execute only when explicitly asked.
Never move/rewrite a published tag; publish a new version for corrections.
## Controlled automation

The installed workflow follows Avo's stable-on-release behavior for this Rust
stack. A successful actual release push can create a read-only version proposal.
Official semantic-release analyzer/notes hooks classify all reachable changes:
breaking MAJOR, feat MINOR, fix or docs(release) PATCH; ordinary docs/test/refactor/
CI/chore changes do not release. Generated chore(release) metadata does not bump
again. No prerelease is generated by this workflow.

After explicit completion confirmation, dispatch `prepare` from main with the
immutable proposal artifact ID and reviewed digest. Bootstrap also needs explicit
confirmation of the manifest's first version. Preparation exports source and uses
an isolated index: it emits a patch, expected tree and metadata manifest without
editing the user's checkout. Only Cargo.toml/Cargo.lock root version tokens and
the dated changelog entry can change; dependency graph drift is rejected.

The owner applies and commits that patch on release with the source as its sole
parent, then pushes. That exact commit needs fresh release-push CI, both light
mutation lanes, a versioned Release ZIP and real native launch/navigation/close.
Source-preview checks cannot certify the later metadata commit.

Dispatch `publish` from main with the preparation artifact ID and final CI
run/attempt/SHA. Read-only preflight freezes source/version, preparation and CI
artifact IDs/digests, tested attachments and approval text. The protected
release-publish reviewer then approves this exact request. The trusted-main
publisher rechecks mutable identities, creates an annotated explicit tag, stages
a draft, downloads and hashes every attachment, and publishes only verified bytes.
Only that job has contents-write permission; no branch writes occur.

An identical release can resume after a transport failure with fresh authorization.
The stable release digest stays bound to immutable tag/draft bytes, while each
approval binds its own control run/attempt. Different source/evidence/assets,
lightweight tags or conflicting existing bytes fail instead of being overwritten.
Expired artifacts need owner intervention. A newer CI attempt requires a new
preflight/approval, even for the same commit.

Promotion to main requires the published release commit/tree/version and does
not calculate or publish another version. Synchronize released ancestry into
develop through user-controlled feature work before the next release cycle.
See [branch setup](branching.md), [local reproduction](development.md#reproducing-ci-locally)
and [implementation evidence](ci-quality-release-validation.md).

Sources: [SemVer](https://semver.org/), [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
[Git annotated tags](https://git-scm.com/docs/git-tag).
